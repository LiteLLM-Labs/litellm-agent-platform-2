Slack Agent Factory - One PR Plan

Ship a platform-level Slack flow where a user can ask the platform bot to create a Claude Managed Agent, configure it for the workspace, and start using it in Slack without manually creating a per-agent Slack app.

Scope: one PR Runtime: Claude Managed Agents Channel: Slack Primary proof: real Slack E2E Build on PR #49 platform MCPs

Goal

A Slack user should be able to DM or mention the platform bot with a request like make me an agent to monitor support escalations. The platform bot should collect missing details, create a Claude Managed Agent, bind it to the correct Slack place, and confirm how to use it.

This PR should not require each new agent to own a separate Slack app. Existing per-agent Slack OAuth can remain supported, but the new flow should use one installed platform Slack app as the broker.

Current State

  • Agents already exist in LiteLLM_ManagedAgentsTable.
  • Claude Managed Agents runtime is supported through claude_managed_agents.
  • Slack event handling exists under src/http/managed_agents/slack/.
  • Slack replies can stream runtime output, react with eyes, and keep thread sessions.
  • Current Slack config is stored per-agent under agent.config.slack.
  • PR #49 adds platform MCP infrastructure at /api/platform-mcps and /mcp/platform/{agent_id}.
  • PR #49 exposes built-in MCP tools read_platform_session and agent_memory.

New Product Shape

  • Install one workspace-level platform Slack app.
  • Route Slack events through a platform broker.
  • Use a platform factory agent for creation requests.
  • Persist bindings from Slack team/channel/user contexts to managed agents.
  • Dispatch normal Slack messages to the bound managed agent.

User Flow

1. Request User messages the platform bot: make me an agent to do X.
2. Clarify Bot asks for missing name, channel, cadence, permissions, or instructions.
3. Confirm Bot summarizes the proposed agent and asks for explicit confirmation.
4. Create Platform tool creates a claude_managed_agents agent.
5. Install Platform completes Slack OAuth if needed, then binds the agent into Slack.

Slack to Agent Landing Flow

This is the exact path from a Slack message like make me an agent to do X to a created Claude Managed Agent that is usable from Slack.

Step Actor Action System Result
1 Slack user DMs or mentions the platform bot: make me an agent to watch support escalations. Slack sends a signed event to /api/slack/platform/events.
2 Platform Slack broker Verifies the request, records the Slack event id, detects creation intent, and opens a factory session. A row is stored in LiteLLM_SlackAgentFactorySessionsTable keyed by team_id, channel_id, and thread_ts.
3 Factory agent Extracts a proposed agent name, instructions, target Slack surface, and missing fields. If required fields are missing, the bot asks a follow-up in the same Slack thread.
4 Slack user Answers follow-ups or clicks Create on the confirmation message. The interactivity callback hits /api/slack/platform/interactivity and resumes the same factory session.
5 Factory agent via platform MCP Calls create_managed_agent with the normalized draft. A new row is written to LiteLLM_ManagedAgentsTable with harness = claude_managed_agents.
6 Factory agent via platform MCP Calls connect_agent_to_slack with the new agent_id, Slack target, and requester context. If the workspace app is already installed, a row is written to LiteLLM_SlackAgentBindingsTable. If not, the tool returns a Slack OAuth install URL and stores a pending install.
7 Slack user Clicks the install URL only when the platform Slack app is not installed for that workspace yet. Slack OAuth redirects to the platform callback, bot token is stored in vault, and the pending agent binding is finalized.
8 Platform bot Posts a confirmation in Slack with the created agent name and usage instructions. The agent has landed in Slack: users can now message the same channel/DM and hit the binding.
9 Slack user Sends a normal top-level prompt where the agent is bound. The broker reacts with eyes, creates a Claude runtime session, streams the reply, and maps the Slack timestamp to that session.
10 Slack user Sends a follow-up in the Slack thread. The broker reuses the parent session and posts the response in the same thread.

Data Model

Table Fields Purpose
LiteLLM_SlackWorkspaceInstallationsTable team_id, team_name, bot_user_id, bot_token_key, installed_by, timestamps One platform Slack app install per workspace. Stores secret references, not token values.
LiteLLM_SlackAgentBindingsTable agent_id, team_id, channel_id, dm_user_id, created_by, status, timestamps Maps Slack surfaces to managed agents. This is the router table.
LiteLLM_SlackAgentFactorySessionsTable team_id, channel_id, thread_ts, user_id, draft_json, status, timestamps Tracks multi-turn creation conversations before an agent exists.
LiteLLM_SlackPendingInstallsTable state, agent_id, requested_by, target_channel_id, target_dm_user_id, expires_at, timestamps Remembers the agent and Slack target while the user completes OAuth. Consumed exactly once by the OAuth callback.

Platform MCPs

This plan should build directly on PR #49. The agent factory should not introduce a second bespoke tool protocol. It should extend the platform MCP catalog and JSON-RPC endpoint already introduced there.

Existing MCP from PR #49 Tool name How the Slack factory uses it
Read platform session read_platform_session Lets an agent inspect platform session messages for handoff, debugging, and explaining what happened during creation.
Read/Write agent memory agent_memory Stores durable agent preferences, Slack onboarding facts, channel policies, and user-provided operating instructions.

New MCPs to expose in this PR

MCP id Input Output Guardrail
create_managed_agent Name, instructions, owner Slack user, model, optional channel/cadence. Agent id and summary. Always creates harness = claude_managed_agents.
connect_agent_to_slack Agent id, requested Slack workspace, channel id or user id, requester Slack user. Either status = connected with binding id, or status = install_required with Slack OAuth URL. Creates a pending install state when OAuth is needed; consumes it once after callback.
list_slack_agent_bindings Team id, optional channel/user filter. Agents visible in that Slack surface. Only returns agents bound to the caller's workspace/surface.
update_agent_instructions Agent id, revised instructions. Updated agent summary. Requires creator/admin or channel-level manager permission.
test_agent_in_slack Agent id, channel/user target, test prompt. Test session id, Slack ts, success/failure. Must not expose token values or raw secrets.

All MCP definitions should appear in platform_mcps() and tool_defs(), with execution in tools/call under /mcp/platform/{agent_id}. The Agents UI should list these tools via /api/platform-mcps and attach them through config.platform_mcp_ids.

Slack Routing

Slack event -> verify platform signing secret -> ignore bot/subtype duplicates -> record Slack event id for idempotency -> if thread is an active factory session: continue agent creation conversation else if message intent is create-agent: start factory session else if channel/dm has binding: route to bound managed agent else: reply with "No agent is connected here yet. Say 'make me an agent to ...'"

OAuth Install Behavior

Creating the platform agent does not require a browser. Installing the platform Slack app into a workspace uses the normal Slack OAuth screen, because Slack requires a human workspace admin/user authorization step.

Workspace state connect_agent_to_slack behavior User experience
Platform Slack app is already installed. Creates the binding immediately and returns status = connected. User sees confirmation in Slack and can use the agent right away.
Platform Slack app is not installed. Creates a pending install row, returns status = install_required, and includes a Slack OAuth URL with a signed state. User clicks the install URL, completes Slack OAuth, returns to the platform callback, and then receives a Slack confirmation.

The OAuth callback must store the bot token in vault, store the workspace installation row, consume the pending install, create the agent binding, and post a final Slack confirmation when possible.

Creation Intent

  • Detect phrases like make me an agent, create an agent, add an agent.
  • Use deterministic phrase matching first.
  • Only call Claude for extraction after the intent is likely.

Confirmation

  • Do not create on vague input without confirmation.
  • Show name, instructions, Slack surface, and runtime.
  • Buttons: Create, Edit instructions, Cancel.

Dispatch

  • React with eyes on accepted messages.
  • Each top-level message creates a new runtime session.
  • Thread replies reuse the parent session and reply in-thread.

Risks

  • Slack app identity: a single platform bot means agents may speak as the platform app unless Slack custom bot identities or clear message prefixes are used.
  • Permissions: channel binding should require the requester to have access to that channel and should not silently add agents to private spaces.
  • Ambiguous requests: the factory must ask follow-ups instead of creating low-quality agents from vague prompts.
  • Token scope drift: new workspace app scopes must be documented and covered by setup checks.
  • One PR size: this is still shippable as one PR, but it should be organized as small modules with focused tests.

PR Acceptance Criteria

  • Passes CI: format, check, clippy, tests, and code-size gate.
  • One workspace Slack app can create multiple agents.
  • Agents created from Slack are Claude Managed Agents.
  • Slack messages route through persisted bindings.
  • Real Slack proof is included in the PR body.
